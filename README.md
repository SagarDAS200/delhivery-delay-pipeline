# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI and ML Certification Program, E&ICT Academy, IIT Roorkee. The data is synthetic (produced by `generate_data.py`); Delhivery is only the setting. Money is in Indian Rupees (INR).

The pipeline answers three questions for the regional operations head: how long a parcel will take (Part B), which parcels will miss their promise (Part C) and which hubs need which playbook (Part D). Part A builds the shared cleaning and feature code that all later parts use.

## How to run

From a fresh clone of the `main` branch:

```bash
pip install -r requirements.txt
python generate_data.py          # prints 24 1224 48, writes data/hubs.csv, raw_shipments.csv, new_shipments.csv
python part_a_clean_eda.py       # data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py      # outputs/part_b_*.csv
python part_c_classification.py  # outputs/part_c_*.csv
python part_d_segments.py        # hub_profile, part_d_separation, hub_segments, segment_profile, tier_vs_segment_mismatch
python package_model.py          # models/*, outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (1.9.1), so if your installed versions differ, re-run `package_model.py` instead of loading the committed file. Every script uses the pinned `random_state` values, and running `predict_delay.py` twice produces byte-identical output.

## Data findings

All numbers come from `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv` and `part_a_correlations.csv`. The 1,224 raw rows contain 24 exact duplicates, leaving 1,200 parcels, of which 278 are delayed (delay rate 0.2317).

1. **Service type.** Express is delayed most often: 119 of 243 Express parcels (delay rate 0.4897), against 0.2056 for Standard and 0.0857 for Economy. The Express promise of 36 hours leaves the least slack.
2. **Hub tier.** The delay rate rises steeply with tier: 0.0400 for Tier 1, 0.2150 for Tier 2 and 0.4400 for Tier 3.
3. **Distance.** The delay rate rises with lane distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km. Beyond 600 km, more than 8 in 10 parcels are late.
4. **Correlation with delivery_hours.** The three most strongly correlated columns are promised_hours (0.8372), distance_km (0.4013) and n_stops (0.3247). promised_hours is the strongest because the service type sets the base time.
5. **Log transform.** declared_value_inr is right-skewed: its mean is INR 1,533.0542 against a median of INR 1,121.5, whereas after the log the mean (7.0277) and median (7.0224) nearly coincide, so the log transform makes the column roughly symmetric.

## Model results (regression)

Source: `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`. The split is 840 / 180 / 180. The scaler was fitted on the training rows only: the scaled training means are 0.0 while the scaled test rows have a largest absolute column mean of 0.2187.

- **Baseline.** Predicting the training mean gives a validation R² of -0.0212, slightly below zero. It explains none of the variation, and every model below is measured against this floor.
- **Validation winner.** Linear regression wins narrowly with an RMSE of 4.8912 hours (R² 0.9313). Gradient boosting is almost tied at 4.9165 (R² 0.9306), the random forest has 5.468 (R² 0.9141) and the decision tree (depth 6) has 6.2796 (R² 0.8867).
- **Bias and variance.** At depth 1 the train RMSE is 11.6334 and the validation RMSE is 12.1324, a gap of only 0.50 with both errors high, which is high bias (underfitting). With no depth limit the train RMSE is 0.0 and the validation RMSE is 7.789, a gap of 7.79, which is high variance (memorising the training rows). The gap grows past depth 6 (3.50 at depth 8, 6.06 at depth 12). Depth 6 has the lowest validation RMSE (6.2796) and was used for the tree.
- **Learning rate.** 0.1 is best (validation R² 0.9306). At 0.01 the model is too slow: 100 small steps leave it underfit (R² 0.7127, RMSE 10.0018). At 1.0 each step overshoots and the model fits noise (R² 0.844, RMSE 7.3701).
- **Cross-validation.** On the 1,020 training-plus-validation rows, gradient boosting scores a mean R² of 0.9352 (std 0.0044) and linear regression 0.9261 (std 0.0048). This ranking is the reverse of the validation ranking, but the validation gap is only 0.025 hours of RMSE on 180 rows, which is noise. I would ship gradient boosting, because the 5-fold estimate uses far more data and the data contain interactions (for example Express during the sale, long distance in rain) that a linear model cannot capture. Following the brief's rule, the final model scored on the test rows was the validation winner, linear regression: test RMSE 4.5235 hours, R² 0.9493. Gradient boosting was not scored on the test rows.

## Model results (classification)

Source: `part_c_*.csv`. The stratified split has 195 / 42 / 41 delayed parcels in train / validation / test.

- **Blind baseline.** Predicting "not delayed" for every parcel gets an accuracy of 0.7667 on validation (138 true negatives, 42 missed delays) but catches no delayed parcel (recall 0). It is useless for operations because accuracy rewards ignoring the minority class. The trained models reach accuracy between 0.8833 and 0.9056 at the default 0.5 rule.
- **Noise columns.** The five bookkeeping columns carry a combined 0.2245 of the forest's importance across 17 columns, even though they carry no signal; random columns still collect importance because trees split on them. By F-score they rank 8, 12, 14, 16 and 17, so all five fall outside the top 7, and each has an F-score below 5 (the highest is 4.5847). The top seven columns all score above 36 (the smallest is sale_event_flag at 36.7281).
- **Choice of k.** Validation F1 for k = 5, 7, 10, 12, 17 is 0.6988, 0.8333, 0.7857, 0.8049 and 0.7848. k = 5 drops two real signal columns and falls sharply; k = 7 keeps exactly the signal columns and is best, with larger k adding noise columns. I used k = 7.
- **Tuning.** Tuning did not beat the untuned forest on validation. The grid search (best CV accuracy 0.8952) reached a validation F1 of 0.775, the randomized search (CV accuracy 0.8905) reached 0.7848 and the untuned forest on the same 7 columns reached 0.8333. The final configuration is therefore the default forest. With only 42 delayed parcels in the validation set, one or two parcels move F1 by several points, so differences of this size are noise, and a validation set that small can select a model by luck.
- **Threshold.** On validation, recall is 0.8333 at threshold 0.5 (precision 0.7955) and 0.7619 at 0.6 (precision 0.8889), so the highest threshold meeting the 0.80 recall rule is 0.5. Lowering it to 0.4 lifts recall to 0.881 but precision falls to 0.74, and 0.1 catches almost everything (recall 0.9762) but with precision 0.4824, so about half the alerts would be false.
- **Test result.** At threshold 0.5, test precision is 0.6889, recall 0.7561 and F1 0.7209 (31 true positives, 10 missed, 14 false alarms). Test recall is lower than the validation recall of 0.8333. With only 41 delayed parcels, three parcels account for most of the gap, so I would not claim the 0.80 recall target holds on new data; the honest reading is that recall is roughly 0.75 to 0.83.

## Operations recommendation

- **Escalate segment (9 hubs, mean delay rate 0.46):** Nagpur (0.46), Kochi (0.36), Patna (0.46), Ranchi (0.38), Guwahati (0.62), Raipur (0.48), Bhubaneswar (0.40), Siliguri (0.44) and Agartala (0.54). The Standard segment (7 hubs) has a delay rate of 0.0257 and the Watch segment (8 hubs) 0.155.
- **Hubs whose tier label misleads** (`tier_vs_segment_mismatch.csv`): Kolkata (Tier 1, behaves like Watch), Nagpur (Tier 2, behaves like Escalate), Kochi (Tier 2, behaves like Escalate) and Dehradun (Tier 3, behaves like Watch). The tier label should therefore not be used to assign playbooks for these four hubs; use the segment instead. Kolkata and Dehradun are better than their label and Nagpur and Kochi are worse.
- **Alert threshold 0.5.** On the test rows, about 7 of every 10 flagged parcels are really delayed (precision 0.6889), and about 7.6 of every 10 delayed parcels are caught (recall 0.7561).
- **New parcels.** Of the 48 new parcels, 8 were flagged: 6 need escalation to a hub manager and 2 need a proactive customer call.
- **Why K = 3.** The across-to-within ratio in `part_d_separation.csv` rises from 2.894 (K=2) to 5.3928 (K=3), 6.3047 (K=4) and 6.8866 (K=5), but the gains after K=3 are small and the K=4 solution (sizes 8-7-5-4) and K=5 solution (8-7-4-3-2) both contain clusters of fewer than 6 hubs, too small to carry their own playbook. K = 3 also matches the three playbooks operations runs.

## Production plan

**(a) Production-readiness characteristics and where they live in the repository**

| Characteristic | Repository item |
|---|---|
| Accuracy | Validation and one-time test scores in `part_c_final_test.csv`; test F1 0.7209 |
| Reproducibility | Pinned `requirements.txt`, fixed `random_state` values, `generate_data.py`, and the run order above |
| Consistency (same preprocessing in training and prediction) | `src/shipment_prep.py` is imported by `part_a_clean_eda.py`, `package_model.py` and `predict_delay.py`; the stored `impute_values.csv` is reused at scoring time |
| Reliability | `part_d_reload_check.csv` (reload difference 0.0) and `feature_order.csv` guarding the column order |
| Maintainability | One script per Part, a single shared module, and every result written to a named CSV |
| Monitorability | `outputs/new_shipment_actions.csv` records probability, flag and action for each parcel, so weekly rates can be computed |

**(b) Quantities to monitor**

1. Weekly delayed share of delivered parcels: investigate if it moves outside 0.23 ± 0.05 (the training rate is 0.2317) for two consecutive weeks.
2. Weekly share of parcels flagged: investigate if it moves more than 5 percentage points away from the share flagged on the validation set (0.2444) for two consecutive weeks.
3. Recall on parcels whose outcome is now known: retrain if it falls below 0.65 over a rolling four weeks (it was 0.7561 on test and 0.8333 on validation).
4. Missing-value share in distance_km, parcel_weight_kg, declared_value and payment_mode: investigate if any column exceeds 5% (the historical rates are 3% or less).

**(c) Retraining and drift.** Retrain monthly on the latest delivered parcels, or immediately when a trigger above fires. Judge the 15-28 September sale window (sale_event_flag) against the same kind of event, for example the previous sale, not against ordinary weeks, because delays are expected to be higher during a sale (the data show an extra 7 hours, and 12 more for Express). Data drift here would look like longer lane distances or more stops per route at a hub, a change in the service mix (more Express), or a hub's delay rate moving away from its segment; the last would mean re-running `part_d_segments.py`.

## Limitations

- The data is synthetic, generated from known formulas, so the very high R² (about 0.93) and clean feature signal will not carry over to real shipment records.
- The test set has only 41 delayed parcels, so test precision, recall and F1 are imprecise; a change of three parcels moves recall by about 7 points.
- The threshold and the final configuration were chosen on one validation split of 180 rows (42 delayed parcels), and the three tuning candidates were separated by only a few parcels.
- Each hub profile rests on 50 parcels, so hub delay rates are noisy (one parcel is 2 percentage points), and K-Means with K = 4 or 5 on 24 hubs can land on different local solutions.
- The models use only dispatch-time features and ignore real-time events such as strikes, road closures or actual weather beyond a single rain flag.
